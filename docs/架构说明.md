# 架构说明

## 请求链路

1. API 或 CLI 接收问题。
2. 如果存在会话历史，先执行问题重写，使省略指代的问题可以独立检索。
3. 向量检索和 BM25 检索并行产生候选结果。
4. 使用 Reciprocal Rank Fusion 融合两路排名。
5. 可选使用 CrossEncoder 对候选进行重排。
6. 将 Top-K 文本块连同来源和页码注入回答提示词。
7. 调用通义千问生成答案，并由服务层单独返回结构化引用。
8. 会话消息写入 SQLite。

## 索引持久化

所有运行数据位于 data 目录：

~~~text
data/
├── manifest.json
├── sessions.sqlite3
├── uploads/
│   └── <document-id>.<ext>
└── index/
    ├── vectors.faiss
    └── chunks.jsonl
~~~

vectors.faiss 保存向量，chunks.jsonl 保存与向量位置一致的文本和元数据。两者必须成对备份。

## 为什么使用混合检索

纯向量检索擅长语义相近的问题，但对编号、金额、专有名词和精确关键词不够稳定。BM25 对精确词项更敏感。RRF 直接融合两路排名，不需要假设向量距离和 BM25 分数处于同一量纲。

## 可扩展点

- 将 FAISS 替换为 Milvus、Qdrant、PGVector 或 Elasticsearch。
- 将 SQLite 会话存储替换为 Redis 或 PostgreSQL。
- 增加 OCR 服务支持扫描 PDF。
- 增加租户字段和行级权限过滤。
- 接入 OpenTelemetry，记录检索耗时、Token、成本和失败率。
- 增加异步任务队列，处理大批量文档导入。
